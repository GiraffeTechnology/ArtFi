# Original project function acceptance matrix

## Purpose and decision rule

This matrix audits all 155 pages of the inherited project file against the current ArtFi branch.
It prevents a historical module from disappearing silently. A row can be accepted in one of four
states:

- `implemented`: current code and local automated evidence exist;
- `scope-adjusted`: the user-visible purpose remains, but the implementation follows the latest
  external-market, external-wallet, RWA, security, and compliance boundary;
- `gated`: the item remains explicitly represented in the roadmap but cannot be enabled in this
  release;
- `gap`: an in-scope function is still missing or lacks runtime evidence and blocks full acceptance.

Screenshots, historic addresses, deployment claims, and named audits in the inherited file are
references only. They are not acceptance evidence. Where the inherited design conflicts with the
latest PRD, the latest PRD controls; the old capability remains visible here as `gated`, not deleted.

## Acceptance result and prioritized gaps

The original file is now fully accounted for, but full product acceptance is **conditional**.
Current P0 UI parity gaps identified by this audit have been closed in the branch. The remaining
current-scope work is P1 or external evidence:

1. P1: runtime analytics or explicit unavailable states, FAQ/help, remaining preferences and
   notifications;
2. P1: admin monitoring/moderation surface, backup/restore drill, and extension-specific acceptance;
3. external: SIN Sepolia receipts, standard probes, OpenSea discovery evidence, legal/compliance and
   security release gates.

Gated items are not considered “missing”: they are explicitly retained and testable as unavailable.
They cannot be re-enabled merely to match a historical screenshot.
