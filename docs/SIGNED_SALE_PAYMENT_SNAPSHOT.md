# Signed-sale payment and block observations

Whole-artwork and direct fractional-sale preflights now read the current buyer's ERC-20 payment-token balance at the same mined block used for seller signature and sale-state checks. Whole sales compare it with the signed exact price; fractions compare it with the bounded fill quantity times the signed unit price. No token decimals, browser floating-point value, other account balance or unrelated asset is substituted. An existing payment allowance is not required at this point because the workflow separately requests the exact required approval.

Both preflights require a mined block number, nonzero block hash and valid chain timestamp. After signature, permission, epoch, ownership/liquidity, payment balance and applicable pilot-cap reads, they re-read the same numbered block and chain identity. Changed number/hash/time or chain identity retires the observation. Existing canonical EOA/EIP-1271 validation, cumulative partial-fill consumption, seller allowances, revocation and pilot limits remain. This is an observation, not a reservation: the market's atomic checks still determine whether a later fill can settle.

A finite 12-second deadline retires a hanging preflight. It does not claim to cancel provider RPCs or roll back an approval that was already confirmed before a later preflight. These read-only helpers cannot broadcast, store a signature or clear a pending/UNKNOWN transaction. Callers retain the original authenticated operation context and transaction journal before each write.

Affected regression cases cover both sale types, exact buyer/token/block reads, insufficient/malformed funds, valid exact-balance fills, post-read chain/reorg drift, missing block evidence, read failure and finite-timeout retirement. Existing signature/ownership/partial-fill/cap negative cases remain. Synthetic RPC results establish helper behavior only; they are not real-chain, actual wallet, deployed-market or full-product acceptance.

The existing whole-artwork and direct fractional listing callers now run the same signed-sale check in the payment-approval callback and again after the approval receipt, immediately before a fill request. The earlier outer duplicate check is removed. Approval confirmation alone cannot carry older balances, epochs or permissions into the fill. Matching-book callers already perform both checks and use the strengthened shared reader.
