# Non-send receipt journal preparation

The existing Wallet receipt runtime has distinct `withPreparation` purposes. `prepare` requires an active, unspent phase. `review` and `observe` validate the original attempt's grant-policy version and can remain available after revocation/expiry so recovery is not stranded. None reserves a new send. An ArtFi native journal read outside that held context is unavailable; opening a preparation gate from inside the send gate would re-enter the store.

`createWholeReceiptPreparedJournal` composes those **existing** purposes with the existing authenticated native task-journal implementation supplied by the trusted installer. It constructs no transport, credential, provider, grant or route. It never falls back to a session journal, listing authorization or an in-memory store. The installer must bind the real mutually authenticated task journal and independently backed grant/journal stores.

- `create(plan, exactWire)` enters `prepare`, matches the full native identity and receipt business to the authenticated snapshot, and uses the existing business/ABI comparator to check the exact ephemeral phase wire. The wire is not included in the journal payload or return value. The native payload retains the complete postgrant principal and IDs and the unchanged full native wire digest. The existing store owns exact idempotence; a progressed returned row is preserved rather than reset.
- `read(purpose, expectedPlan?)` derives the native operation ID from the complete original principal. It sends only that ID through `review` or `observe`. Every returned row is checked for the original principal/phase, deployment domain, all sale and eight correspondence fields, wallet/chain, full-plan/request hash, lifecycle, revision and timestamp. An optional expected full plan additionally binds the original native plan ID and every exact plan byte represented by the existing canonical digest.
- Context is rechecked after every native await and before publication of any result. Nested/duplicate context callbacks are refused. A create acknowledgement failure preserves uncertainty; recovery reads the same derived operation rather than inventing another identity or triggering a wallet call.
- Only `get` and `create` exist on this port. No update, send, signing, phase reservation or wallet-start-marker reset is added. Reconciliation updates must retain their existing independently verified canonical chain/Kit proof and only-forward CAS policy; they are not a generic extension of read permission.

Both results explicitly carry `executionAuthorization: NOT_ESTABLISHED` and `approvalCommitments: CONTENT_MATCHED`. The existing application pregrant producer now recomputes the approved business/association content inside the held policy binding for creation and every returned recovery row. See [Receipt content boundary checks](WHOLE-RECEIPT-CONTENT-BOUNDARIES.md) and [Approval commitment records](WHOLE-RECEIPT-APPROVAL-COMMITMENTS.md) for the exact namespaces and normalization. Content equality does not establish that a registration proof was accepted on chain. A native row is not a new approval, Kit admission, source-authenticity verdict or proof of physical delivery.
