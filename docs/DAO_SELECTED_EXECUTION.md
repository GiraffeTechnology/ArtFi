# Selected DAO proposal execution

The governance console used to retain its last submitted package while allowing an unrelated Proposal ID to be inspected. Queue and execute could still use that saved package. Both controls now require an exact selected-ID match. The saved package remains visible, with an explicit reselection action and a link to the existing published-proposal execution page for proposals from other members or browsers.

Before a wallet request, the console reuses the existing published-proposal reader to recover terms from the original successful creation receipt and verify the configured Governor/Vault/token/action registry on Hoodi. The current state must permit the requested operation; execution requires the queued proposal's elapsed chain-time timelock. A new current holder read uses the same observation block, followed by simulation with the exact account, operation and recovered terms. Chain identity and both canonical block identities are checked after simulation. A changed selection, wallet context or operation lease retires the preflight. These observations do not reserve chain state: the existing contracts remain authoritative at execution.

Reading never clears a pending wallet prompt, an UNKNOWN transaction or a saved package. The original DAO action session owns the request marker, hash, replacements and reconciliation. No new signer, authentication route, deployment parameter, grant, payment or buyout-settlement authority is introduced.

The new bounded unit cases exercise real receipt decoding and the reused reader through a synthetic chain adapter. The standalone browser fixture mounts the actual governance console, selected-action helper and original action journal; only wagmi wallet/RPC hooks are adapted. It exercises selection mismatch, current membership refusal, simulation refusal, selection/account departure, UNKNOWN reconciliation and elapsed timelock execution. These checks do not establish real wallet signatures, public RPC, deployed contracts, full Next application or full-product acceptance. Run them only on an existing approved remote test server, using the existing dependencies and browser. No download or install is required by the fixture scripts.
