# ADR-0002:ArtFi 专用 L2 —— 设计与是否应当建设的判断

| 项 | 内容 |
| --- | --- |
| 状态 | **草案,待决策** |
| 日期 | 2026-09-05 |
| 画像 | 低频交易、单笔金额大 |
| 已确认的三项约束 | 驱动 = 降低交易成本 + 原生支持 ERC-9999 投影语义;支付腿 = 链下法币与链上稳定币并存;节点准入 = 无许可 |
| 前置事实 | 仓库中此前无任何 L2/rollup 工作;现有合约约 1,600 行,Sepolia only,市场以 ERC-20 托管撮合 |

---

## 一、结论先行

**按"低频 + 大额"这个画像,专用链的两项驱动经不起计算,建议不建。** 下面先给数,再给理由,最后按你的选择把设计做完——**若仍决定建设,第三节就是完整方案,不是敷衍。**

### 1.1 成本驱动不成立

以太坊 L1 一次完整结算(挂单 + 成交 + 清算)约 280,000 gas。12 gwei、ETH $3,000 下约 **$10**。

| 成交额 | 手续费占比 |
| --- | --- |
| 10 万元 | 0.073% |
| 100 万元 | **0.0073%** |
| 1000 万元 | 0.0007% |

对照:拍卖行佣金 **10–25%**,支付通道 1–3%。

**在大额场景里,L1 手续费已经是噪声。** 造一条链去省一个 0.007% 的成本,同时把大额资金放进一座新桥,方向是反的:省下的是小数点后第三位,承担的是本金。

### 1.2 盈亏平衡点在"低频"的定义之外

自建 rollup 的固定月成本(保守下限,**未含建设与审计**):

| 项 | 月成本 |
| --- | --- |
| L1 有效性证明验证(1 批/天 × 400k gas) | $432 |
| blob 数据可用性 | $60 |
| 基础设施:排序器、证明者、监控、RPC、值班 | $5,000 |
| **合计** | **$5,492** |

**盈亏平衡 = 545 笔/月 ≈ 18 笔/天。**

| 月交易量 | 自建单笔 | L1 单笔 |
| --- | --- | --- |
| 20 笔 | $274.60 | $10.08 |
| 50 笔 | $109.84 | $10.08 |
| 200 笔 | $27.46 | $10.08 |
| 1,000 笔 | $5.49 | $10.08 |

"低频"按定义就落在平衡点以下。**要让自建更便宜,前提是不再低频**——这与画像自相矛盾。

而且真正的大头不是 gas:一条 rollup 加一座桥的**建设与审计**是数人年的工程,桥的单次审计通常就是五位数到六位数美元,且必须反复做。这笔钱在上表中一分未计。

### 1.3 ERC-9999 不需要原生支持

投影接口是 ERC-165 可探测的**合约接口**,设计目标就是任何 EVM 链都能实现。把它做成链的原生能力有两个问题:

1. **与标准的目的相反。** 一个 ERC 的价值在于可移植;做成某条链的原生语义,等于把它变成只在自家链上成立的东西,而我们正在推的是一份公开标准。
2. **省不到关键的那一段。** 投影本身的 gas 开销很小(追加一条记录 + 两次比较);真正贵的是证明验证——签名恢复与默克尔路径。这两项在 EVM 上**已经有预编译**(`ecrecover`,必要时 EIP-2537 的 BLS)。自建链在这里几乎没有额外空间。

### 1.4 "无许可 + 低频 + 大额"是三者中最难的一条

无许可验证者需要经济理由才会存在。低频意味着手续费收入趋近于零,于是只能靠发币补贴——**那就变成用一个你控制不了市值的代币,去保护大额实物资产**。安全预算低于被保护价值,正是大额场景最不能接受的失败形态。

**唯一干净的解法是 based rollup**(见 3.2):排序权直接继承以太坊的提议者集合,不需要新的验证者经济,也不需要发币。第三节的设计据此展开。

### 1.5 建议

| 场景 | 建议 |
| --- | --- |
| 大额、低频的权属与结算 | **直接用以太坊 L1**。手续费占比 0.007%,换来最强的结算保证与最小的攻击面 |
| 小额、二级市场、碎片化份额 | **用现成 L2**(Base / Arbitrum / OP)。你的几十笔搭在别人每月数百万笔上,固定成本已被摊掉 |
| 何时重估自建 | 当**月交易量稳定超过 ~500 笔**,或出现计算不出来的非成本理由(下节) |

**会改变这个结论的,不是成本,而是控制权。** 若日后出现"必须在协议层强制持有人白名单、必须能执行冻结/更正指令、成交价与持有人不宜全网公开"这类要求,那是造专用链的正当理由——但那时要的多半不是 rollup,而是许可链,且与本次"无许可"的选择直接冲突。

## 二、若仍决定建设:必须先接受的三件事

1. **单笔成本会上升,不会下降。** 在达到 ~545 笔/月之前,自建比 L1 贵,量越小差得越多。
2. **桥是主要失窃面。** 大额稳定币会沉淀在桥合约里。历史上 L2 的重大损失绝大多数发生在桥,而不是执行层。
3. **低频意味着可能没人在看。** 这一条决定了下面的技术选型,详见 3.3。

## 三、设计(按已确认的三项约束)

### 3.1 总体形态

**以太坊 L1 上的有效性 rollup(ZK validity rollup),基于排序(based sequencing),blob 数据可用性,带强制包含与逃生舱。**

```
                以太坊 L1(结算 + 数据可用性 + 排序权来源)
                 │
                 ├── ArtFiRollup.sol      状态根、证明验证、强制包含队列
                 ├── ArtFiBridge.sol      NFT 与稳定币的托管,分额度分时限
                 └── blob(EIP-4844)      每批交易数据
                 ▲
                 │ 每批:交易数据 + 有效性证明
                 │
     ┌───────────┴───────────┐
     │   ArtFi L2 执行层      │   EVM 等价
     │   现有 1,600 行合约    │   RWARegistry / Vault / Fractional
     │   直接迁移             │   Market / Governor / 9999 投影
     └───────────────────────┘
```

### 3.2 为什么是 based sequencing:它解决的正是"无许可"那一条

普通 rollup 的排序器是一个需要被信任、也需要被激励的角色。低频下没有手续费养它,于是要么中心化(与"无许可"冲突),要么发币(安全预算 < 被保护价值)。

**Based rollup 把排序权交回 L1 提议者**:任何一个以太坊提议者在轮到自己出块时,都可以把本 L2 的下一批交易纳入。

- 排序**天然无许可**,直接继承以太坊的提议者集合;
- **不需要新代币、不需要新验证者经济**;
- 活性与抗审查等同于以太坊本身;
- 代价:出块节奏跟随 L1 slot(12 秒级),没有"软确认即时性"。**对低频大额,这个代价可以忽略——本来就没人在追求毫秒确认。**

> 需诚实标注:based rollup 是相对较新的形态,生产级实现与工具链的成熟度不及主流 OP Stack / Orbit 路线。选它是为了满足"无许可"这一条,**代价是工程风险更高**。若可以放宽到"联盟排序",工程复杂度会显著下降。

### 3.3 为什么必须是有效性证明,不能是乐观 rollup

**这一条是全篇最重要的技术判断。**

乐观 rollup 的安全性依赖一个前提:**在挑战窗口内,至少有一个诚实方在盯着,并且愿意付 gas 提交欺诈证明。**

低频链恰好破坏这个前提:一条每月二十笔的链,**很可能一个观察者都没有**。守望者没有经济理由存在,而攻击者只需要在无人值守的窗口里提交一次错误状态根。**大额 + 无人看守 + 七天窗口 = 最坏组合。**

有效性证明没有这个依赖:状态转换正确性由证明本身保证,不需要任何人在看。

**附带好处**:没有七天挑战期,提款延迟从"七天"降到"下一批被证明"。这对大额资金的流动性是实质改善。

**代价**:每批要付一次证明生成与 L1 验证(已计入 1.2 的 $432/月)。低频下这笔钱摊不薄——这正是 1.2 结论的一部分。

### 3.4 数据可用性:必须用 blob,不能用 validium

Validium 把数据放链下,便宜,但一旦数据不可得,用户**无法自证余额、无法退出**。大额场景下这个交换不成立。

用 EIP-4844 blob:每天一个 blob 约 $2 量级,相对被保护的金额可以忽略。**这是本设计中少数"贵一点但必须买"的项。**

### 3.5 桥:按被保护金额设计,而不是按功能设计

桥是主要失窃面,因此不按"能用"设计,按"被偷了会怎样"设计:

| 机制 | 作用 |
| --- | --- |
| **分资产隔离金库** | NFT 与稳定币分别托管于独立合约,一处被攻破不牵连另一处 |
| **提款速率限制** | 单位时间内可提出的稳定币总额设上限,超过则排队。**这是唯一能把"一次性掏空"变成"分批掏空并被发现"的机制** |
| **大额延时** | 超过阈值的提款强制等待 N 小时,期间任何人可触发暂停 |
| **多方暂停键** | 暂停可由多方中任意一方触发(低门槛),恢复需要高门槛。**暂停要容易,恢复要难** |
| **无升级的资产合约** | 托管资产的合约不可升级;需要变更时迁移而非改写 |
| **独立的桥审计** | 与执行层分开审计,且在每次桥变更后重做 |

> **速率限制会拖慢大额提款,这是有意的。** 低频画像下这个摩擦几乎不被感知,却是唯一能限制单次损失上限的手段。

### 3.6 双支付腿

已确认:大额走链下法币,小额与二级市场走链上稳定币。**两条路径必须在同一个权属记录上收敛,否则会出现"链上说成交了、链下没付钱"或反过来。**

- **链上稳定币腿**:现有 `ArtFiMarket` 的托管撮合直接迁移,原子成交——付款与权属转移在同一笔交易内完成,不存在中间态。
- **链下法币腿**:这正是 **ERC-9999 投影**要解决的问题。链上不承载付款事实,只承载登记册的确认结果:
  - 法币结算完成 → 登记方在链下登记册记入变更 → 经证明准入一条投影条目;
  - 结算在途期间,链上如实呈现"缺口开启、该时刻被争议、尚未终局";
  - **代币在此期间不被阻断转让**——这是标准的核心主张,也是与 PRD 现行"冻结"要求的正面冲突(见下)。
- **一致性规则**:任一标的在任一时刻只能走一条腿。链上腿成交即 `ownerOf` 变更;链下腿只改投影。**消费方读哪一个,由权利条款决定,不由链决定。**

### 3.7 ERC-9999:合约,不是预编译

按 1.3 的理由,投影以**普通合约**实现并迁移到 L2,与 L1 上的实现保持字节级一致。

L2 侧唯一值得考虑的原生化,是把远端终局性证明的验证做成预编译——但只有当 profile 采用 EVM 无预编译支持的签名方案(如某些 BLS 曲线)时才有意义。**当前 profile 用 `ecrecover`,不需要。**

### 3.8 强制包含与逃生舱(不可省)

- **强制包含队列**:用户可直接在 L1 提交一笔 L2 交易;若排序方在 N 个区块内未纳入,该交易可被强制上链。这保证任何人**在被审查时仍能退出**。
- **逃生舱**:若 L2 停止出块超过阈值,用户可凭默克尔证明直接在 L1 从桥中提取自己的资产。
- 二者都是**大额场景的前提条件**,不是可选特性。没有它们,"无许可"只是排序无许可,而资产实际上被扣在一个可以停机的系统里。

### 3.9 治理与升级密钥

**升级密钥是比桥更隐蔽的攻击面。** 一个能即时升级 rollup 合约的多签,等价于能拿走桥里所有资产。

- 所有可升级组件加**强制时间锁**,时间锁长度不短于逃生舱触发窗口——保证用户能在恶意升级生效前退出;
- 托管资产的合约不可升级(见 3.5);
- 升级提案与时间锁倒计时全部上链可观测。

## 四、若决定建设:分期,且每一期都能独立止损

| 阶段 | 内容 | 止损点 |
| --- | --- | --- |
| **0. 先不造链** | 大额走 L1,小额走现成 L2;把 ERC-9999 投影与双支付腿在 L1 上跑通 | 若量始终上不去,到此为止即可,没有沉没成本 |
| **1. 量化触发条件** | 埋点统计真实月交易量与金额分布 | 未稳定超过 ~500 笔/月则不进入下一阶段 |
| **2. 桥与逃生舱先行** | 在现成 L2 上先建桥、速率限制、强制包含、逃生舱,并完成独立审计 | 桥审计不过关则停止 |
| **3. 执行层** | 迁移 1,600 行合约,基于 based sequencing 起链 | — |
| **4. 证明系统** | 接入有效性证明,逐步收紧升级密钥 | — |

**阶段 0 不是拖延,是当前唯一有数据支撑的方案。**

## 五、必须先解决的一处正面冲突

ERC-9999 规定:**缺口开启期间普通转让不得被阻断**。
而 PRD §6/§7 要求:待交割期间**阻止 NFT 转让**、进入**不可转让**状态。

**标准禁止的正是 PRD 要求的。** 这不是措辞差异,是规范性冲突,且无论是否建链都必须先裁决——它决定 3.6 的链下法币腿到底怎么写。

现有 `settlement-coordinator.js`、`consumer-state-machine.js` 按 PRD 实现,即当前实现与我们正在推的标准不一致。

## 六、本 ADR 未做的事

1. 未做威胁建模与形式化安全论证——若进入阶段 2,桥必须单独做。
2. 未评估任何具体技术栈的实现成熟度(OP Stack / Orbit / based rollup 的生产可用性)。
3. 1.2 的基础设施成本是**下限估计**,未含人力;真实成本大概率数倍于此。
4. 未考虑监管对"自建链"的态度——若日后出现许可链诉求,本设计的"无许可"前提需整体重估。
